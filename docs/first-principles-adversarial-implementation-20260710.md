# 商圈比价采集系统第一性原理与对抗式实现基线

更新日期：2026-07-10

## 1. 第一性原理

系统的价值不是“页面可打开”或“脚本能运行”，而是在外部渠道、网络、设备、账号和人工响应都不可靠的前提下，仍能持续产出完整、真实、可追溯的门店商品数据。

因此生产验收只围绕五个问题：

1. 数据会不会丢失或被错误标记为完整。
2. 同一账号、浏览器席位或类目会不会被重复执行。
3. Master、Worker、网络、Redis、对象存储短时故障后能不能恢复。
4. 内部使用者能不能在一个入口内看懂进度并完成干预。
5. 故障发生后能不能在五分钟内定位到门店、类目、采集席位和失败阶段。

## 2. 设计要求对照

| 设计要求 | 当前实现 | 本轮加固 |
|---|---|---|
| 单一系统入口 | 已实现 | 删除双工作台残留结论，两个 URL 同一入口 |
| Master-Workers 调度 | 已实现 | 保留 PostgreSQL 事实源和 fenced lease |
| 数据完整性 | 已实现主体 | 继续以 `completed_valid` 和原始产物门禁为唯一完成口径 |
| 账号/Profile/CDP 绑定 | 已实现 | 继续在资源页提供必要的高级详情，不在首页堆叠底层字段 |
| 前端业务语义 | 部分实现 | 首页和公共状态改为业务语言，技术标识按需展示 |
| 实时连接容灾 | 未完整 | WebSocket 自动重连，重连后重新同步快照 |
| API 降级 | 未完整 | GET 超时和有限重试，写操作不盲目重试 |
| Master 依赖降级 | 未完整 | Redis/S3 探针超时、明确 503、Redis 事件旁路失败不破坏数据库主链路 |
| Worker 防重复 | 部分实现 | 账号席位领取前互斥，防止轮询重入重复领取 |
| Worker 网络失败 | 部分实现 | 所有 Master HTTP 请求增加超时，关键可重放写入继续使用本地 spool |
| 可观测性 | 部分实现 | 增加 HTTP、WebSocket、依赖和调度指标 |
| 弹性扩展 | 已具备水平扩展基础 | 维持无状态 Master 接口、数据库租约和多 Worker 横向扩展模型 |

## 3. 对抗式场景

### 3.1 浏览器打开但数据停止更新

- 攻击路径：Master 重启、Wi-Fi 抖动、浏览器休眠导致 WebSocket 关闭。
- 旧行为：页面永久停留在旧快照。
- 目标行为：指数退避重连；重连成功后重新获取完整快照；页面明确显示同步状态。

### 3.2 轮询重入导致同一席位领取两个任务

- 攻击路径：一次领取请求超过轮询间隔，下一次轮询再次进入。
- 旧行为：任务返回前没有占用标记，存在并发领取窗口。
- 目标行为：从 CDP 可达性检查开始锁定账号席位，直到领取结束或任务执行结束。

### 3.3 Redis 短时不可用导致心跳写入失败

- 攻击路径：PostgreSQL 已写入心跳，但 Redis `SET/PUBLISH` 抛错。
- 旧行为：Worker 收到错误，可能重复上报；数据库事实与调用结果不一致。
- 目标行为：PostgreSQL 为事实主链路；Redis 旁路超时后记录告警并降级，不回滚已成功心跳。

### 3.4 外部依赖无限等待

- 攻击路径：Redis、MinIO、Master HTTP 建连但不返回。
- 旧行为：就绪探针或 Worker 请求长时间挂起。
- 目标行为：所有依赖调用有明确超时；就绪探针返回各依赖状态和 HTTP 503；Worker 保存断点并停止推进。

### 3.5 技术信息淹没业务判断

- 攻击路径：首页直接展示端口、协议和内部路径，异常只显示底层错误。
- 旧行为：业务人员难以回答“哪个门店、哪个类目、采了多少、是否需要我处理”。
- 目标行为：首页以门店、类目、商品数、采集设备和待处理事项为主；必要技术绑定只在资源与诊断页面展示。

### 3.6 本机路径和内部标识泄漏到页面

- 攻击路径：采集错误、Profile 配置或对象存储记录包含绝对路径、长 URL、对象键和请求码。
- 旧行为：页面直接显示长路径，挤压业务信息且对使用人员没有价值。
- 目标行为：前端不展示绝对路径、对象键、长 URL 或内部请求码；原值仅保留在数据库、原始产物和诊断日志中。

## 4. 不做的事情

- 不引入验证码绕过、账号风控规避或代理池自动切换。
- 不把 Redis 作为任务或数据唯一事实源。
- 不对非幂等写请求进行浏览器侧自动重试。
- 不为了名义上的微服务拆分而增加部署点；当前规模使用清晰模块和持久状态机获得更高可靠性。
- 不将旧批次或缺少真实到手价证据的数据标记为完整可交付。

## 5. 本轮完成标准

- 单一入口无模式切换残留。
- 前端断线可自动恢复，GET 请求有超时和有限重试。
- Master 的 `/ready` 能在依赖故障时快速返回 503 和故障依赖。
- Redis 旁路故障不破坏已成功的 PostgreSQL 心跳主链路。
- 同一账号/CDP 席位不存在轮询重入窗口。
- 指标覆盖 HTTP 请求、错误、延迟、在线连接、任务、风险、租约和数据量。
- 自动化测试、类型检查、构建、浏览器回归和至少一项故障注入通过。

## 6. 实施与验证结果

- Dashboard 已收敛为单一入口，`/` 与 `/?final=20260710` 使用同一应用状态树。
- 前端读取请求具备 8 秒超时和一次有限重试；写请求不自动重试。
- Dashboard WebSocket 使用指数退避重连，受控关闭旧连接后成功建立新连接，连接状态从 `CLOSED` 恢复为 `OPEN`。
- Master `/ready` 并行检查 PostgreSQL、Redis 和对象存储，并返回延迟和独立错误。
- Redis 故障注入期间，`/ready` 在 136ms 内返回 HTTP 503；Redis 恢复后系统重新就绪。
- 故障注入前后结构化商品均为 11,457，SKU 均为 16,548，证明 Redis 故障没有影响数据库事实数据。
- Master 实时事件通过 Redis 跨实例广播；Redis 不可用时仍保留当前实例本地广播和数据库主链路。
- Worker Master 请求具有 10 秒超时；账号/浏览器席位在领取请求发出前加锁，消除轮询重入窗口。
- 商品结构化和质量校验进入单并发异步队列，与多个浏览器采集子进程形成逻辑隔离和背压。
- 全部 12 个页面完成可见文本扫描，不再展示绝对路径、长 URL、对象键、内部请求码或采集游标。
- 已移除任务表的“手工结单”入口，任务只有通过原始数据、结构化和质量门禁后才能成为 `completed_valid`。
