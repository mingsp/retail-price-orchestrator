> 项目代号：Retail Radar

> 推荐定位：分布式任务调度 + 数据生产平台 + 人工介入恢复系统

## 一、项目包装与事实边界

本项目不应包装成单机页面脚本或接口破解工具，也不能虚构为平台官方合作项目。更准确、合规且有技术含量的描述是：

> 面向即时零售多源页面商品与价格数据，构建一套多设备、多账号、多浏览器 Profile、长周期运行、允许失败、可暂停恢复、可人工介入、可审计的数据生产与调度平台。

推荐使用以下业务表述：

- 即时零售多源商品与价格数据。
- 业务授权终端上的浏览器自动化任务。
- 不稳定外部数据源、登录会话异常和人工验证。
- 低频、可暂停、可追溯的数据生产链路。
- 页面展示价格快照、SPU/SKU 标准化与质量校验。

不建议在简历或面试中使用以下表述：

- 绕过风控、反爬突破、账号防封、指纹伪装、代理池对抗。
- 破解或逆向某平台内部接口。
- 推断或声称掌握平台内部数据库、微服务或风控实现。
- 使用商家后台、非公开权限或其他无法证明合规性的描述。

如面试官追问数据来源，可如实回答：

> 数据来自业务人员有权访问的即时零售页面。项目重点不在高频抓取，而在多设备调度、低频执行、失败恢复、人工介入、原始数据留存和数据质量。系统不依赖对目标平台内部架构的假设，也不把绕过验证作为系统能力。

## 三、项目为什么有含金量

### 1. 它解决的是分布式调度问题，不是单机脚本问题

系统的基本资源关系是：

```text
Worker 设备
  -> Browser Slot
      -> CDP 运行快照
      -> Chrome Profile
      -> 登录账号
      -> 当前目标门店
          -> 门店批次
              -> 固定类目任务
```

关键约束包括：

- 同一类目任务只能被一个合法 Worker 领取。
- 同一账号、Profile 或 Browser Slot 不能并发执行冲突任务。
- Worker 离线或租约过期后，任务可以重新分配。
- 旧 Worker 恢复后不能覆盖新 Worker 的进度与产物。
- 页面门店与任务门店不一致时，只阻断当前任务，不能误停整个批次。

实现中以 PostgreSQL 作为控制面事实源，而不是把 Redis 分布式锁当作唯一真相。Redis 负责事件与辅助状态；即使 Redis 暂时不可用，任务事实和业务查询仍由 PostgreSQL 保持。

### 2. 它采用 At Least Once + 幂等，而不是虚构 Exactly Once

网络超时、进程退出和重复上报都可能导致操作重放。系统通过以下组合收敛重复和乱序：

- 数据库行锁与条件状态迁移。
- 每次任务分配递增 `lease_generation`。
- 进度、产物、质量结果均执行 fenced write guard。
- 门店、批次、类目、SPU、SKU 等业务身份参与唯一性校验。
- 对象存储使用精确 `versionId`，不把“相同 object key”误认为同一份实物。

这比简单声明“消息只消费一次”更符合真实分布式系统语义。

### 3. 它把浏览器运行时纳入了领域模型

CDP 端口会变化，因此不能把端口当作稳定业务身份。系统引入稳定的 Browser Slot，并绑定：

- 物理 Worker。
- Chrome Profile。
- 登录账号标识。
- CDP 当前运行快照。
- 当前目标门店与风险状态。

该模型解决了多设备、多窗口环境中最容易发生的“看错浏览器、用错账号、采错门店、异常后无法定位”问题。

### 4. 它同时建设控制面、执行面和数据面

```text
控制面：任务、租约、账号、Profile、Browser Slot、风险事件
执行面：Worker、Chrome/CDP、检查点、进程生命周期
数据面：原始 JSONL、截图、日志、SPU/SKU、质量清单、业务导出
```

三者解耦后，Worker 可以独立扩容，Master 可以统一调度，原始数据也不会因业务字段调整而丢失。

### 5. 它以数据完整交付为终点

“执行进程退出码为 0”不能代表门店数据完整。系统交付前会检查：

- 目标类目是否都有独立原始产物。
- MinIO 实物大小和 SHA-256 是否与登记一致。
- 冻结批次读取的是否为登记时的精确对象版本。
- 原始 `productRaw.skus[]` 展开数量是否与结构化 SKU 一致。
- 页面展示价等关键字段覆盖率是否达到门禁。
- 门店、批次、账号、Profile 和任务身份是否一致。

任一关键对账失败，批次不能标记为有效完成。

## 六、面试展开话术

### 问题 1：为什么不用 Redis 分布式锁直接抢任务？

建议回答：

> Redis 可以提升事件和临时状态处理效率，但任务状态、租约和写入资格必须在同一事务事实源内完成。项目使用 PostgreSQL 行锁和条件更新领取任务，使“领取任务”和“更新任务状态”处于同一事务；Redis 故障时系统降低就绪状态，但不会丢失任务事实。

### 问题 2：Fencing Token 解决了什么问题？

建议回答：

> Lease 只能判断租约是否过期，无法阻止暂停很久的旧 Worker 在恢复后继续写数据。每次重新分配都会递增 `lease_generation`，所有进度、产物和质量写入都校验 owner 与 generation。旧 Worker 即使恢复网络，也会因 generation 过期而被拒绝，从而避免脑裂写入。

### 问题 3：怎样保证任务只执行一次？

建议回答：

> 分布式环境中不承诺物理意义上的 Exactly Once，而采用 At Least Once 执行、幂等写入、唯一业务身份和状态校验。任务可以重试，但旧租约不能写，新旧产物通过批次与对象版本隔离，最终数据通过质量门禁收敛为唯一有效交付。

### 问题 4：为什么同时保存 JSONL 和结构化表？

建议回答：

> 结构化字段和业务规则会变化，只保留清洗结果会失去重放能力。因此原始 JSONL 作为不可变权威层，MinIO 保存精确版本和校验和；SPU/SKU 价格表只是可重建的业务投影。字段调整时可以从原始层重新生成，不需要重新访问外部数据源。

### 问题 5：如何判断一次门店任务真正完成？

建议回答：

> 不以脚本退出码为准，而以数据交付门禁为准。系统校验类目覆盖、原始产物实物、SHA-256、对象版本、原始 SKU 展开数、结构化 SKU 数及关键价格覆盖率，全部通过后才冻结批次并生成业务导出。

### 问题 6：Codex 在系统里应该承担什么职责？

建议回答：

> 确定性的任务领取、续租、检查点、上传和状态迁移由 Worker 与状态机完成；Codex 适合部署在 Master 侧，读取风险事件和上下文后判断异常类型，调用白名单幂等动作辅助恢复。它不直接操作数据库，也不是系统正确性的唯一依赖。目前该 Supervisor 属于下一阶段，不能描述为已生产上线。

## 七、面向不同岗位的表达重点

### Java 后端开发岗位

优先强调：

- PostgreSQL 事务、行锁、条件更新和并发任务领取。
- Lease、Fencing Token、幂等和状态机。
- Redis 故障降级与事实源边界。
- MinIO 不可变数据资产和 MySQL 事实表。
- 故障注入、E2E 和生产门禁。

不要因为应聘 Java 岗就把 TypeScript/Fastify 改写成 Spring Boot。可以说明：

> 当前系统使用 Fastify 实现，但调度一致性、数据模型和故障恢复机制与语言无关；若迁移到 Java，可使用 Spring Boot、JDBC/MyBatis 和同样的 PostgreSQL 事务语义实现。

### AI Agent 研发岗位

优先强调：

- 确定性状态机与智能 Supervisor 的职责边界。
- Human-in-the-loop 风险处理。
- Agent 只调用白名单、幂等、可审计的恢复动作。
- 原始数据与上下文证据支撑异常判断。
- Agent 不应替代租约、数据库约束和质量门禁。
