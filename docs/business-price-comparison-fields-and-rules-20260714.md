# 商圈比价字段说明与价格比较规则

文档状态：正式业务口径
发布日期：2026-07-14
适用范围：我方门店与竞对门店的美团 H5 商品价格比较
数据表：`fact_store_spu_price_snapshot`、`fact_store_sku_price_snapshot`

## 1. 业务目标

本项目不是比较商家后台结算价，也不是在数据库中预先计算一个统一的“比较价”。项目需要回答的是：

> 对于用户认为是同一件商品、同一规格的商品，我方门店和竞对门店在页面上分别显示多少钱，我方比竞对贵多少或便宜多少。

因此，数据库只保存采集到的价格事实、商品识别信息、优惠约束和采集批次。独立比价脚本负责：

1. 选择我方门店批次和竞对门店批次。
2. 识别双方是否为同一商品、同一规格。
3. 判断价格是否具备可比性。
4. 分别计算页面展示价、优惠到手价和折扣力度。
5. 输出 Excel、CSV 或分析报告，不把临时比价结果回写到两张事实表。

## 2. 三种价格的业务语义

| 字段 | 用户页面含义 | 完整性 | 比价用途 |
|---|---|---:|---|
| `front_display_price_amount` | 商品列表或商品页最主要、最醒目的当前展示价格 | 100% | **主比价价格** |
| `user_final_price_amount` | 页面明确给出的券后、首件、会员等优惠后到手价 | 约 7% | 独立的优惠价比较，不替换主展示价 |
| `original_price_amount` | 页面划线价或原价 | 100% | 计算折扣力度，不作为成交价比较 |

### 2.1 主价格口径

商圈日常比价统一使用：

```text
我方页面价 = 我方 front_display_price_amount
竞对页面价 = 竞对 front_display_price_amount
```

不能使用以下做法：

```text
COALESCE(user_final_price_amount, front_display_price_amount)
```

原因是它会把一方的有条件优惠价与另一方的普通页面价混在一起，造成“看起来便宜、实际口径不同”的错误结论。

### 2.2 到手价口径

`user_final_price_amount` 为空是正常情况，不代表漏采。只有满足以下条件时，才生成到手价比较：

1. 双方均存在大于 0 的到手价。
2. 优惠适用范围相同或可解释，例如都是首件价、都是普通用户可领取券。
3. 起购量、限购量、会员条件等没有造成明显口径差异。
4. 商品和规格已经确认匹配。

若只有一方存在到手价，脚本应输出“该门店存在额外优惠”，但不得把它与另一方页面价直接计算为正式价差。

### 2.3 划线价口径

`original_price_amount` 用于计算页面宣传折扣：

```text
折扣率 = front_display_price_amount / original_price_amount
优惠金额 = original_price_amount - front_display_price_amount
```

划线价不是用户当前支付价格，禁止与另一家门店的页面展示价直接比较。

## 3. SPU 表字段说明

SPU 表一行表示某门店、某采集批次中的一个商品主体。最终结构共 17 个字段。

| 字段 | 含义 | 为什么需要 | 比价脚本如何使用 |
|---|---|---|---|
| `id` | 数据库自增主键 | 便于定位、分页和审计单行记录 | 不参与商品匹配和价格计算 |
| `batch_id` | 本次门店采集批次 ID | 防止不同日期的数据混用，保证重复同步幂等 | 脚本必须明确选择我方批次和竞对批次 |
| `snapshot_hour` | 商品采集时间，上海时区并精确到小时 | 页面价格会随时间变化，需要知道价格对应时间 | 检查双方是否来自同一比较周期，并在结果中展示 |
| `channel_code` | 数据渠道，当前为 `meituan_h5` | 为未来接入其他平台保留渠道边界 | 不同渠道默认不直接比较，除非脚本明确允许 |
| `store_code` | 门店稳定编码 | 门店名称可能变化，编码用于稳定识别门店 | 区分我方和竞对具体门店，组成业务唯一键 |
| `store_name` | 采集时的门店名称 | 让业务结果可读，并保留历史名称 | 展示在比价结果中，不作为唯一识别依据 |
| `store_role` | 门店角色：`own` 或 `competitor` | 明确哪一方是我方、哪一方是竞对 | 决定价差方向，必须一方为 `own`、一方为 `competitor` |
| `category_name` | 门店页面原始类目名称 | 用于结果分组、筛选和运营分析 | 只用于分组，不能仅凭同类目认定为同一商品 |
| `category_order` | 类目在门店页面的原始顺序 | 保持业务查看顺序稳定 | 用于 Excel 和页面排序，不参与价格计算 |
| `source_spu_id` | 平台来源 SPU ID | 在同一门店和渠道内稳定定位商品主体 | 组成业务唯一键；不同门店的来源 ID 不能直接互相匹配 |
| `standard_spu_id` | 跨门店统一后的标准 SPU ID | 让不同门店的同一商品主体建立稳定关系 | SKU 无法匹配时，按该字段做 SPU 级兜底比较 |
| `product_name` | 页面采集到的原始商品名称 | 商品识别和人工复核的核心信息，禁止改写 | 用于候选匹配和结果展示；名称相似不等于确认匹配 |
| `front_display_price_amount` | 页面主展示价 | 用户最直接看到的价格，也是本项目主口径 | 双方主价差和价差率均使用此字段 |
| `user_final_price_amount` | 有明确页面证据的优惠后到手价 | 捕捉券后、首件等更具吸引力的价格 | 仅在双方优惠条件可比时单独比较；为空不报错 |
| `original_price_amount` | 页面原价或划线价 | 反映促销力度，且实际数据中多数不等于展示价 | 只计算折扣，不作为当前成交价 |
| `promotion_text` | 页面优惠文案 | 解释低价是否有会员、首件、限时等条件 | 判断到手价是否可比，并随异常低价输出 |
| `match_status` | 匹配状态：`matched`、`unmatched`、`review` | 防止未经确认的候选商品直接进入正式比价 | 只有 `matched` 进入正式结果，`review` 进入人工复核 |

SPU 业务唯一键：

```text
batch_id + store_code + source_spu_id
```

## 4. SKU 表字段说明

SKU 表一行表示某门店、某采集批次中一个具体商品规格。最终结构共 25 个字段。与 SPU 表重复的批次、门店、类目和价格字段语义完全一致。

| 字段 | 含义 | 为什么需要 | 比价脚本如何使用 |
|---|---|---|---|
| `id` | 数据库自增主键 | 定位和审计单行 SKU | 不参与匹配和价格计算 |
| `batch_id` | 门店采集批次 ID | 隔离不同采集周期 | 明确选择双方批次，禁止跨周误比 |
| `snapshot_hour` | SKU 价格采集小时 | 记录价格时间点 | 检查时效并展示在结果中 |
| `channel_code` | 数据渠道 | 隔离不同平台的数据语义 | 默认只比较相同渠道 |
| `store_code` | 门店稳定编码 | 稳定区分门店 | 组成业务唯一键并确定比较双方 |
| `store_name` | 门店名称 | 业务可读性 | 输出结果展示 |
| `store_role` | 我方或竞对角色 | 决定比较方向 | 价差统一按“我方减竞对”计算 |
| `category_name` | 页面原始类目 | 结果分组和筛选 | 不作为同品判定条件 |
| `category_order` | 页面类目顺序 | 保持输出顺序 | 仅排序使用 |
| `source_spu_id` | 平台来源 SPU ID | 关联 SKU 所属商品主体 | 用于 SKU 归组和 SPU 回退 |
| `source_sku_id` | 平台来源 SKU ID | 精确定位来源规格 | 组成 SKU 业务唯一键 |
| `standard_spu_id` | 标准 SPU ID | 跨门店统一商品主体 | SKU 未能确认时作为 SPU 级回退依据 |
| `standard_sku_id` | 标准 SKU ID | 跨门店统一到同一商品规格 | **SKU 精确比价的首选匹配键** |
| `product_name` | 页面原始商品名称 | 防止匹配错商品并方便人工核对 | 候选召回、冲突校验和结果展示 |
| `spec_name` | 原始规格，例如 500ml、24 罐 | 同商品不同规格不能直接比较总价 | 精确匹配规格；规格不同则禁止直接总价比较 |
| `upc` | 商品条码 | 高可信的标准商品识别信息 | UPC 相同时可作为强匹配证据，但仍需核对规格 |
| `front_display_price_amount` | SKU 页面主展示价 | 用户看到的该规格当前价格 | SKU 主比价价格 |
| `user_final_price_amount` | SKU 优惠后到手价 | 保留真实优惠事实 | 双方条件可比时独立计算优惠价差 |
| `original_price_amount` | SKU 原价或划线价 | 分析该规格促销力度 | 只计算折扣，不当作成交价 |
| `promotion_text` | SKU 或 SPU 优惠文案 | 解释优惠资格和低价条件 | 判断到手价、0.01 元价格是否具有可比性 |
| `min_purchase_quantity` | 最低起购数量 | 单件价格可能要求一次购买多件 | 起购量不同时必须提示，不得无条件比较 |
| `limit_purchase_quantity` | 单次或活动限购数量 | 首件价和引流价通常有限购 | 低价结果必须附带限购信息；`-1` 按来源语义视为不限购 |
| `stock_quantity` | 采集时库存或可售数量 | 无库存商品虽有价格但当时不可购买 | 库存为 0 时不进入主可售商品排行榜 |
| `sale_status` | 可售状态：`available`、`out_of_stock` 等 | 将来源状态转成业务可理解的可售判断 | 主比价只使用 `available`，缺货记录单独保留 |
| `match_status` | 匹配状态 | 阻止错误候选进入正式结果 | 只有 `matched` 进入正式 SKU 比价 |

SKU 业务唯一键：

```text
batch_id + store_code + source_spu_id + source_sku_id
```

## 5. 商品匹配规则

价格是否正确，首先取决于商品是否匹配正确。脚本必须按照以下顺序处理。

### 5.1 SKU 精确匹配

满足任一强证据并通过名称、规格冲突检查后，才可标记为 `matched`：

1. 双方 `standard_sku_id` 相同。
2. 双方 UPC 相同，且 `spec_name`、包装数量一致。
3. 已经人工确认并固化为同一标准 SKU。

以下情况不能直接比较总价：

- 500ml 与 1L。
- 单瓶与整箱。
- 普通版与无糖版。
- 不同口味、型号或适用人群。
- 赠品装与普通装。

### 5.2 SPU 兜底匹配

当 SKU 无法精确匹配，但双方 `standard_spu_id` 相同时，可以输出 SPU 级比较。SPU 结果必须标记“规格未完全确认”，不能伪装成 SKU 精确比价。

### 5.3 未匹配和待复核

- `unmatched`：不进入正式比价。
- `review`：进入人工复核清单，不进入正式价格结论。
- 类目相同、名称相似只能生成候选，不能直接改成 `matched`。

## 6. 正式比价计算规则

### 6.1 输入参数

比价脚本每次必须显式接收：

```text
我方门店 store_code
我方采集 batch_id
竞对门店 store_code
竞对采集 batch_id
允许的最大采集时间差，默认 24 小时
比较层级：SKU 优先，SPU 兜底
```

我方和竞对批次 ID 本来就不同，脚本不能使用 `batch_id` 相等作为双方关联条件。

### 6.2 SKU 主价格比较

进入正式计算的记录必须同时满足：

1. 双方 `standard_sku_id` 相同且 `match_status='matched'`。
2. 双方 `sale_status='available'`。
3. 双方 `front_display_price_amount` 非空且大于 0。
4. 双方采集时间处于允许的同一比较周期。
5. 规格和包装数量没有冲突。

计算公式：

```text
价格差额 = 我方页面展示价 - 竞对页面展示价
价格差异率 = (我方页面展示价 - 竞对页面展示价) / 竞对页面展示价
```

解释：

- 差额小于 0：我方便宜。
- 差额等于 0：双方同价。
- 差额大于 0：我方更贵。

金额计算必须使用十进制数，结果至少保留 2 位小数，禁止使用浮点数直接做财务判断。

### 6.3 SPU 回退比较

当 SKU 无法匹配时，只有双方 `standard_spu_id` 相同且 `match_status='matched'` 才能进入 SPU 回退结果。SPU 价格差额仍使用双方 `front_display_price_amount`，但结果中必须明确标记 `comparison_level='SPU'`。

### 6.4 优惠到手价比较

到手价另起一组指标：

```text
优惠价差额 = 我方 user_final_price_amount - 竞对 user_final_price_amount
优惠价差异率 = 优惠价差额 / 竞对 user_final_price_amount
```

双方任一到手价为空，正式优惠价差即为空，只输出哪一方存在优惠及对应优惠文案。

### 6.5 折扣力度比较

双方分别计算自己的页面折扣：

```text
我方折扣率 = 我方页面展示价 / 我方原价
竞对折扣率 = 竞对页面展示价 / 竞对原价
```

该指标表示页面促销力度，不代表绝对价格更低。例如 20 元商品打五折仍可能比 8 元商品更贵。

## 7. 特殊场景处理

| 场景 | 正确处理方式 |
|---|---|
| 只有竞对存在到手价 | 主比较仍为双方页面价；额外标记“竞对有优惠到手价” |
| 双方都有到手价，但一个是会员价 | 不直接生成正式优惠价差，进入优惠条件复核 |
| 页面展示 0.01 元 | 保留真实页面价，同时输出限购量、起购量和优惠文案 |
| 页面价格为 0 的售后或配送说明 | 识别为非商品入口并排除，不当作免费商品 |
| 同名但规格不同 | 不比较总价；未来可在单位换算可信时增加单位价分析 |
| 商品缺货 | 保留价格快照，但不进入当前可购买商品主榜 |
| 双方采集时间相差过大 | 标记“时间不可比”，不生成正式价差结论 |
| 商品名称相似但匹配未确认 | 保留为 `review`，由业务人员复核 |

## 8. 比价脚本输出建议

比价结果属于脚本产物，不属于两张来源事实表。业务输出建议包含：

| 输出字段 | 含义 |
|---|---|
| 标准 SKU/SPU | 双方商品关联标识 |
| 商品名称 | 我方和竞对原始名称并列展示 |
| 规格 | 双方规格并列展示 |
| 我方页面价 | 我方 `front_display_price_amount` |
| 竞对页面价 | 竞对 `front_display_price_amount` |
| 页面价差额 | 我方页面价减竞对页面价 |
| 页面价差异率 | 页面价差额除以竞对页面价 |
| 我方到手价 | 可为空 |
| 竞对到手价 | 可为空 |
| 优惠条件 | 双方优惠文案、起购和限购信息 |
| 我方原价/竞对原价 | 用于折扣分析 |
| 库存状态 | 说明价格是否可购买 |
| 比较层级 | `SKU` 或 `SPU` |
| 可比性状态 | 可比、优惠条件待复核、规格待复核、时间不可比 |
| 采集时间 | 双方 `snapshot_hour` |

## 9. 数据质量门禁

### 9.1 必须阻断

- 页面展示价缺失。
- 门店、批次、商品来源 ID、商品名称或采集时间缺失。
- 同一业务唯一键出现重复记录。
- 已标记 `matched` 但标准 SKU/SPU 缺失。
- 到手价小于等于 0，或没有原始来源证据却被写成到手价。

### 9.2 允许为空

- `user_final_price_amount`：没有明确优惠时正常为空。
- `promotion_text`：没有优惠文案时正常为空。
- `standard_spu_id`、`standard_sku_id`：尚未完成匹配时为空。
- `upc`、`spec_name`：来源未提供时为空，但会降低自动匹配可信度。

不能用非空率决定字段是否有价值。到手价覆盖低但业务价值高；比较价覆盖高但可由其他字段计算，因此已经删除。

## 10. 当前数据基线

| 数据层级 | 行数 | 页面展示价 | 原价/划线价 | 有证据到手价 |
|---|---:|---:|---:|---:|
| SPU | 14,805 | 14,805（100%） | 14,805（100%） | 1,140 |
| SKU | 20,646 | 20,646（100%） | 20,646（100%） | 1,441 |

当前两个生产批次跨库逐业务键审计结果：缺失 0、多余 0、商品与价格字段差异 0、重复业务键 0。

当前 `standard_spu_id`、`standard_sku_id` 尚未填充，`match_status` 仍为 `unmatched`。因此现有价格事实已经可用，但在形成正式“我方与竞对同品价差”之前，必须先完成标准 SKU/SPU 映射，不能仅凭商品名称自动输出正式结论。

## 11. 最终业务原则

1. 主比价只比较双方页面主展示价。
2. 到手价与页面价分开比较，不混成一个字段。
3. 原价只用于折扣分析。
4. SKU 精确匹配优先，SPU 只做兜底。
5. 先确认同品同规格，再计算价格差。
6. 低价必须同时解释限购、起购、会员和库存条件。
7. 数据库保存事实；脚本负责匹配、选择口径和生成比价结论。
