# 66 业务 Worker 生产交接

## 1. 节点定位

66 已完成开发部署，后续由业务人员自行登录账号、填写标识、选择门店并执行采集。开发侧负责升级、故障修复和平台能力，不代替业务持续跑数。

66 不承担 201 总控职责，不接收其他 Worker 的历史 JSONL，也不保存 201 的数据库或 MinIO 备份。

## 2. 固定资产

| 资产 | 位置或标识 |
|---|---|
| Codex 打开的工程 | `D:\SpanAI\retail-price-orchestrator` |
| 独立节点运行根目录 | `C:\ProgramData\RetailRadar\Standalone` |
| Worker 运行根目录 | `C:\ProgramData\RetailRadar\Worker` |
| CDP 端口 | `19661` 至 `19665` |
| Profile | `rr66-xcgjz-01` 至 `rr66-xcgjz-05` |
| 远程桌面 | `<66_WORKER_LAN_IP>`，仅局域网可访问；真实地址在节点私有交接文件中维护 |

现场已验证 66 Master 与 Worker 均为 `0.2.18`。5 个 Browser Slot、可编辑标识页、登录页、CDP 命令闭环、RDP、监控、告警、备份和回滚均已部署。

## 3. 业务开跑顺序

1. 通过远程桌面进入 66。
2. 在每个 Profile 的标识页先填写账号标识、归属人和目标门店。
3. 再在对应登录页完成人工登录；不要由脚本提交短信或验证码。
4. 页面能显示正确门店商品后，才把席位标记为可调度。
5. 先执行一个小类目 Canary，再扩大到固定类目分工。
6. 一个账户完成自己的类目后，只接管仍未完成的其他类目；不得重复领取已完成类目。
7. 出现验证码时保留页面和 checkpoint，人工处理后恢复；出现 403/418 时按风险手册隔离账号/Profile。

## 4. 数据边界

- 66 的历史 JSONL 不因代码部署而上传或复制到 201。
- 新任务产生的原始产物只通过正式 artifact 上传链进入所属 Master。
- 本地过程目录保留到 Master 确认 artifact、checksum、对象版本和交付冻结完成。
- 不将多个类目的同一商品合并；同一商品出现在神券和普通类目时保留两条类目事实。
- Excel 由 Master 的正式交付接口生成，Worker 不用零散 JSONL 临时拼表交付。

## 6. 开发与业务的完成边界

- “部署完成”：服务在线、CDP/RDP/监控/备份可用，业务能够自行登录和创建任务。
- “业务完成”：指定门店全部冻结类目校验通过，原始产物齐全并生成 Excel。

两者必须分开记录，不能因部署完成而把门店数据标成 100%。
