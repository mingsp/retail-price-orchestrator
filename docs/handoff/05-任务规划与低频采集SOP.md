# 任务规划与低频采集 SOP

## 目标

用尽可能少的请求取得尽可能完整的门店原始数据，同时确保账号、Profile、门店和类目分工可追溯。

## 任务粒度

正式任务按“门店批次 + 类目”拆分。一个账号负责一组固定类目：

- 不让多个账号同时采同一类目。
- 不让同一账号跨门店混采。
- 账号完成分配后，可以承接明确迁移的剩余类目。
- 迁移必须更新 Master 绑定和 lease，不能只口头切换。

## 当前采集主链路

```text
页面真实运行时
  -> 类目计划
  -> 页面缓存商品
  -> allSortedSpuId
  -> 缺失 ID 动态 smooth fill
  -> raw JSONL
  -> checkpoint / progress / summary
```

生产脚本：

```text
scripts/native-cdp-store-capture.mjs
```

## 请求策略

- 不固定假设每次只能返回 20 条。
- 动态 chunk 只能依据当前页面方法和返回结果调整。
- 优先读取页面已有缓存。
- 只请求 `allSortedSpuId` 中缺失的商品。
- 不重复请求 checkpoint 已证明落盘的商品。
- 新账号先自然进入门店和浅层类目，不从旧账号深页直接请求。
- 不通过频繁点击类目制造请求。
- 页面 fallback 默认关闭，只有明确批准才启用。

建议初始基线：

- 请求间隔：45～120 秒随机。
- 类目间休息：90～240 秒随机。
- 风险休眠：至少 1 小时或等待人工确认。
- 动态 chunk：`balanced`。

基线可以在 Canary 后调整，但必须记录账号、门店、请求数、速度和风险结果。

## 启动前

1. 创建门店批次。
2. 获取页面当前类目计划。
3. 固定账号和类目分配。
4. 核对 Browser Slot 和门店。
5. 检查已有 checkpoint 和原始文件。
6. 确认输出目录和 capture ID。
7. 执行一个小类目 Canary。

## 采集中

业务摘要只保留：

- 门店。
- Worker/Slot/脱敏账号。
- 当前类目。
- 已采原始 SPU、嵌套 SKU。
- 类目完成数和有效缺口。
- 请求数与最近成功时间。
- 风险和人工待办。

不要逐请求发送钉钉。钉钉只发风险、50% 和 100% 等有效里程碑。

## 类目完成

一个类目只有在以下条件满足时完成：

- checkpoint 标记完成。
- 缺失 ID 为 0，或有明确可解释缺口。
- raw JSONL 非空并可解析。
- 商品名称未改写。
- 嵌套 SKU 可展开。
- 展示价质量检查通过。

营销类目和常规类目可能重叠；报告时分开统计门店唯一商品和类目关系。
