# 账号风控、Profile 与登录操作手册

## 1. 目的和边界

本手册让第一次接手的人能够在出现 403、418、验证码、登录失效、商品不可见时做出一致、
可审计的处置。目标是停止错误请求、保护账号、保留断点并恢复授权采集，不是绕过平台限制。

任何限制均不得通过伪造身份、复制 Cookie、验证码自动化、代理池轮换或连续试号规避。

## 2. 先区分四种对象

| 对象 | 典型问题 | 状态 | 是否可继续领取任务 |
|---|---|---|---|
| Account | 验证码、目标门店 403、登录失效、业务线限制 | `safe/running/cooldown/manual_required/blocked/retired` | 仅 `safe` |
| Profile | 留有风险页面、商家后台、旧账号会话或异常历史 | `safe/profile_risk_pending/profile_risk/retired` | 仅 `safe` |
| Worker/网络 | 同设备多个独立账号共同异常、出口或定位异常 | `healthy/risk_watch/device_risk/offline` | 仅 `healthy` |
| Task | 验证、租约丢失、页面不匹配、等待人工 | `running/manual_required/sleeping/paused/requeued` | 按状态机 |

账号恢复正常不自动证明 Profile 安全；主页正常也不证明即时零售门店可采。

## 3. 风险发生后的第一分钟

无论是 403、418、验证码还是商品不可见，固定执行：

1. 停止该 Browser Slot 的新商品请求和类目切换。
2. 保留当前页面，不连续刷新，不直接重启全部浏览器。
3. 固化 checkpoint、raw JSONL 文件大小、最近成功类目和最后成功商品 ID。
4. 记录 Worker、Slot、脱敏账号、Profile、CDP、门店、类目和发生时间。
5. 保存页面标题、可见错误、状态码和截图 artifact，不保存 Cookie 或完整动态 URL。
6. 创建风险事件并把任务置为 `manual_required` 或 `sleeping`。
7. 只在人工确认后执行下文的单次只读分类检查。

## 4. 403 分类决策

403 是现象，不是最终结论。一次受控检查只回答“限制发生在哪一层”，不能连续刷新探测。

| 页面组合 | 判定 | 账号动作 | Profile 动作 | 任务动作 |
|---|---|---|---|---|
| 只有目标门店 403，其他同类门店可见 | `target_poi_block` | 对该门店冷却 | `profile_risk_pending` | 迁移该门店剩余类目 |
| 普通店可见，多个即时零售门店 403 | `instant_retail_block` | 退出即时零售任务并冷却 | `profile_risk_pending` | 不再分配同业务线 |
| 门店首页可见，商品区或加载动作 403 | `product_interface_block` | 停止采集 | 保留并观察 | 从最后有效 raw/checkpoint 停住 |
| 普通外卖与即时零售都 403 | `waimai_or_account_block` | `blocked` 或人工复核 | `profile_risk` | 换健康资源 |
| 同设备多个独立账号出现相同 403 | `device_or_ip_risk` | 不继续加新号 | 当前 Profile 全部观察 | 暂停该 Worker 新任务 |
| 同账号换健康设备仍对目标业务线 403 | `account_block` | 冷却或退役 | 原 Profile 保持隔离 | 换备用账号 |
| 页面正常、采集器单次收到 403 | `interface_403` | 先冷却，不判死号 | `profile_risk_pending` | 禁止原参数重试 |

分类检查结束后立即停止，不用更多门店或更多账号“验证猜测”。

## 5. 418、验证码和登录异常

### 418 或请求异常

1. 停止当前接口和当前类目。
2. 不改变 chunk、参数或深页位置反复重试。
3. 标记 `interface_418`，账号进入冷却，Profile 进入观察。
4. 人工从页面正常入口检查是否出现验证。
5. 恢复时从浅层页面和有效 checkpoint 开始，不复用失败请求参数。

### 验证码或身份核验

1. 标记 `manual_required`，保留页面。
2. 通知中写清 Worker、Slot、脱敏账号、目标门店和风险类型。
3. 由授权人员在正确窗口完成验证。
4. Worker 只做低频页面状态检查，不连续刷新。
5. 验证后重新核对账号、门店 ID 和商品可见性，再做 Canary。

验证码反复失效、授权码过期或页面循环返回验证时，不继续尝试；隔离该账号/Profile 并人工复核。

### 登录失效

1. 暂停任务并确认当前 Slot 身份。
2. 不在未知 Profile 中直接输入账号。
3. 人工重新登录原账号前，确认 Profile 仍为 `safe`。
4. 登录后更新脱敏账号标识和最后确认时间。
5. 门店、账号和任务绑定一致后才能恢复。

## 6. 新账号登录 SOP

新账号不能登录到旧风险 Profile。固定步骤：

1. 在 Master 创建新的 Browser Slot 或为备用 Slot 分配新的 `profile_id`。
2. 在 Worker 创建全新的纯采集 Profile 目录，不复制旧 Profile。
3. 启动唯一 CDP，打开标识页，不自动弹出门店操作。
4. 标识页填写 Worker、Slot、CDP、完整登录手机号、账号所属人和目标门店，并点击“保存标识”。
   完整手机号只留在本机标识页；Master 回传脱敏号。
5. 确认该 Profile 未登录商家后台、商家端或其他无关业务系统。
6. 使用稳定、合规且定位正确的网络，由人工完成登录。
7. 不在配置、日志、文档或 Master 中保存密码、短信码和完整 Cookie。
8. 登录后先核对账号标识，再只读打开目标门店首屏。
9. 门店 `poi_id_str`、标题、商品可见性全部一致后，执行一个小类目 Canary。
10. Canary 和原始数据验收通过后，账号状态才可设为 `safe`。

禁止复制旧 Profile 的 Cookie、localStorage、UUID、访问参数、请求签名、验证页或深页游标。

## 7. 换号加换 Profile 的完整链路

当账号确认受限、验证码长期无法完成或 Profile 已污染时：

1. 冻结旧任务 lease，记录最后有效 checkpoint 和 raw 文件哈希。
2. 将旧账号标记为 `cooldown`、`blocked` 或 `retired`，填写原因和复检时间。
3. 将旧 Profile 标记为 `profile_risk` 或 `retired`。
4. 关闭旧 Slot 的采集进程；不删除旧 Profile，不清除审计证据。
5. 从账号池选择已授权、未冷却、未绑定其他活跃 Profile 的备用账号。
6. 创建新的纯采集 Profile 和新的稳定绑定。
7. 更新包外私密账号映射，并在新标识页填写新手机号、所属人和目标门店。
8. Codex 必须在当前直接任务中明确提醒新手机号、所属人、Worker、Slot/CDP 和目标门店；
   钉钉与审计只显示脱敏手机号。
9. 按“新账号登录 SOP”完成人工登录和首屏预检。
10. 只迁移任务计划、已完成类目、已落盘商品 ID 和 checkpoint 版本。
11. 不迁移 Cookie、页面会话、旧接口参数或失败深页请求。
12. 新账号先执行缺口类目的浅层 Canary。
13. Canary 通过后，使用商品 ID 去重续采；不得把已有商品全量重采。
14. 风险事件记录旧资源去向、新资源绑定、迁移点和恢复证据。

Codex 换号提醒使用固定格式：

```text
账号更换完成
Worker/Slot/CDP：<RESOURCE_ID>
新手机号：<从包外私密账号映射读取的完整手机号>
所属人：<OWNER>
目标门店：<STORE>
Master 脱敏标识：<MASKED_LOGIN>
下一步：请在新 CDP 标识页确认并保存，然后人工登录。
```

该提醒只发在当前直接 Codex 任务中，不转发钉钉群，不写运行日志。

## 8. Profile 生命周期

```text
new -> safe -> running -> profile_risk_pending -> safe
                               \-> profile_risk -> retired
```

- `new`：刚创建，尚未完成登录和 Canary。
- `safe`：纯采集、绑定唯一账号、现场预检通过。
- `running`：正在执行固定门店的固定类目。
- `profile_risk_pending`：出现单次 403/418/验证，等待分类和复检。
- `profile_risk`：风险已确认，不得登录新账号。
- `retired`：永久退出调度，目录保留至审计和保留期结束。

端口变化不代表新 Profile；新目录和新 `profile_id` 才是新 Profile。

## 9. 冷却和复检

冷却不是自动恢复证明。风险事件必须明确 `cooldownUntil` 和复检对象。

1. 当天不反复打开目标门店。
2. D+1 或批准时间执行一次只读复检。
3. 复检顺序为登录状态、普通业务页面、即时零售非目标门店、目标门店首屏。
4. 目标门店仍异常则延长冷却或退役，不进入商品加载。
5. 复检通过后仍需小类目 Canary，不能直接恢复深层缺口。
6. D+1 目标门店异常应计入账号使用成本和下次调度策略。

具体冷却时长由当前业务负责人批准；历史 24～48 小时只是经验范围，不是永久固定值。

## 10. 设备和网络升级条件

出现以下任一情况，停止该 Worker 新账号登录并升级处理：

- 同设备两个或以上独立账号在相近时间出现同类即时零售 403。
- 多个全新纯采集 Profile 表现一致，而其他设备正常。
- 地址定位、时区或网络出口与目标业务区域明显不一致。
- 同账号在其他健康设备可用，但在本设备持续异常。

先核对网络模式、定位、系统时间和页面，再决定是否恢复。不得通过频繁更换代理地区或代理池试错。

## 10.1 门店定位和搜索

目标门店可能只在相应配送范围内可搜索。固定顺序：

1. 由运营确认目标门店地址和附近配送位置。
2. 在 Master 门店策略中配置 `locationPreflight` 中心点和允许半径。
3. 人工在 H5 地址选择器中选择目标门店附近位置。
4. Worker 读取页面 `actualLat/actualLng`，Master 校验距离。
5. 位置通过后再搜索或打开目标门店。
6. 最后以 `poi_id_str` 做不可变门店校验，不能只看相似名称。

位置缺失或距离超出范围时记录 `store_location_mismatch` 并阻断任务。不得通过修改 CDP 地理位置
或反复搜索试错代替人工地址选择。

## 11. 恢复门禁

同时满足以下条件才可恢复：

- Worker 心跳、Slot、CDP 状态正常。
- 账号状态允许该业务线和目标门店。
- Profile 为 `safe`，并与账号唯一绑定。
- 页面不是登录、验证码、403/418 或空商品页。
- 门店 ID 与任务一致。
- checkpoint 和 raw JSONL 可解析且没有回退。
- Canary 成功，商品名称、SKU 和展示价字段可见。
- 风险事件已记录处理人、恢复证据和任务去向。

缺少任一项都保持暂停。

## 12. 新人最容易犯的错误

- 看到 403 就刷新、换参数或重打深页。
- 主页能开就认为账号健康。
- 用新账号登录旧风险 Profile。
- 只换 CDP 端口但继续使用同一个 Profile 目录。
- 把商家后台和消费者采集登录在同一 Profile。
- 换号后从零采集，造成重复请求。
- 迁移旧 Cookie、UUID、页面参数或失败请求。
- 多账号同设备异常时继续加号试。
- 验证完成后不核对门店就恢复。
- 只看进度 100%，不检查 raw、checkpoint 和质量门。

## 13. 事件记录模板

使用 `config/templates/risk-event.example.json`。账号和 Profile 生命周期使用
`config/templates/account-profile-lifecycle.example.json`。模板中只能填写脱敏账号标识，不填写密码、
短信码、Cookie、完整手机号、完整动态 URL 或本机绝对路径。
